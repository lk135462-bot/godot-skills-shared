# 像素遊戲場景開發管線（Pixel Game Scene Pipeline）

## 角色定位

本 Skill 是一個像素等角宿舍模擬專案用兩輪返工換來的場景開發方法論。核心問題：**AI 產圖怎麼變成引擎裡「活的、統一光影的、可互動的」遊戲場景**。最貴的教訓一句話：場景走「整張全生成再摳件」，角色走「離散 sprite」——兩者管線不同，混用即返工。

第二輪實戰（設計簡報流、門系統、shader 光影、一鍵驗收、多 agent 並行、構圖鎖迭代）經驗已併入：§0 設計先行、§1 門策略、§3 鐵則 7–8、§5 shader 分工與驗收地板、§6 專職路由與檔案鎖、§7 UX 情境稽核。

**引用時機**：
1. 任何像素／pixel-ish 遊戲場景（房間、樓層、剖面、地圖）要用 AI 產圖時 → 先讀 §1 決策管線再發第一張工單。
2. 場景圖已產出、要接進引擎（Godot / canvas）時 → §4 工具鏈＋§5 引擎模式。
3. 場景美術驗收時 → §2 驗收基準＋§3 鐵則集。
4. 凡場景含**室內格局**（動線／連通／樓梯／乾濕分區）→ 產前產後**必過 `interior-space-sanity` Skill**（空間運用八原則＋審圖檢查表，本 Skill 不重複其內容）。
5. 要**從零設計新空間格局**（新房間／新樓層／新場景）時 → 先走 §0 設計先行（設計包 → 簡報確認 → 定案才產圖），**別直接讓 AI 生成**。
6. 需要**引擎渲染前置設定**（stretch mode／texture filter／pixel snap／畫布解析度）、**TileMapLayer tile 場景**、攝影機／光影／匯出設定時 → 讀 `godot-game-dev` Skill 的 `References/godot-pixel-art.md`。
7. 產圖驗收要**像素品質理論與機械前哨**（色盤白名單／alpha 二值／mixels 往返測試）→ 本 skill `References/pixel-art-fundamentals.md`；**AI 產圖工具選型** → `References/ai-pixel-art-tools.md`。
8. 要替**已存在且已有合格素材的系列**補角色、動作、服裝、特效或場景變體時 → 先走下方「既有系列生成譜系閘門」，不得先重寫一套看似相近的新提示詞。

## §0 設計先行：先設計 → 簡報確認 → 產圖（產圖之前）

**取代「直接讓 AI 生成」**。教訓：AI 整圖生成**壓不住拓撲**——房間鄰接、動線連通說變就變；根治法是**設計期把鄰接關係人工鎖死**，定案才產圖。流程三步：

1. **設計 agent 出設計包**：空間格局先由設計 agent 產出「**動線＋風格＋物品清單＋平面示意圖**」的完整設計包（鄰接／動線 → level-designer；風格／氛圍 → game-visual-storyteller，路由見 §6）。
2. **簡報確認**：設計包走 `slide-builder` 產**原生 Google Slides** 給使用者確認；格局定案才發第一張產圖工單。
3. **產圖**：帶著定案格局進 §1 管線。

### 簡報＝對齊介面（單一對齊面）

視覺設定／守則用**原生簡報**當唯一對齊面，不散落在對話裡：

- **per-page 秒級重建**：簡報建置腳本要支援 `--pages N` 只重建指定頁、**不碰手插圖片**；`--notes-only` 只改講者備忘錄。整份重生 = 手動插的圖全丟。
- **每頁講者備忘錄寫「該頁的更新指令」**——未來任何 session 的 agent 看備忘錄即知怎麼重建這一頁。
- **驗收標準沉澱在簡報頁上**——通過／打回的判準跟著設定走，不用翻對話。

### 尺度基準從現有素材量出（不憑空設尺寸）

- 量**現有人物 sprite** 回推比例尺（例：場景站姿 108px → 1m≈63.5px），門高／床長／桌面高全從此換算。
- **平面圖上放人物剪影當比例尺**——使用者一眼可驗「床睡不睡得下、門過不過得去」。

### 設計投影要對齊成品投影（俯視平面圖 ≠ 等角產圖依據）

2D 俯視平面圖不能直接當等角剖面的產圖依據——設計期就做「**等角化**」轉換，據此**重排格局**：

- footprint 畫成**菱形**（等角網格），不是俯視矩形；
- 明定**近側牆剖除**——窗／招牌別畫在會被剖掉的近側牆（三假影見 §3 鐵則 7）；
- 家具以 **3/4 視角**思考擺放，處理**深度遮擋**關係；
- **招牌件朝剖口**擺，避免重要視覺元素落在死角。

## §0.5 既有系列生成譜系閘門：複製已驗收配方，不靠目測重造

當專案已保留合格素材與生成紀錄時，**原始生成譜系是第一權威來源，成品圖只負責驗收，不是拿來猜配方的唯一依據**。補角色或補動作前先搜尋同系列的 sheet、manifest、prompt、佇列、session／生成紀錄、模型設定與後處理腳本；找到後把已通過的配方參數化，結構性內容原樣保留，只替換角色身分、服裝、招式／動作與必要的語意變數。

### 產前 provenance preflight

每個既有系列至少建立一份可回讀的 `generation_recipe`（JSON、YAML 或 Markdown 均可），記錄：

- 已驗收來源素材與版本／hash；
- 原始正向提示詞、負向提示詞及不可改的結構段落；
- 模型／工具／版本，以及可取得的 seed、quality、steps、CFG、denoise 等參數；
- 輸出尺寸、長寬比、sheet 格數、幀順序、角色比例、基線與留白；
- 每張參考圖的**角色分工**（身分錨、風格錨、姿勢錨、構圖鎖），不可把不同用途混成「都參考」；
- 背景／alpha 策略，以及去背、despill、裁切、分幀、縮放、減色、匯入設定等後處理順序與腳本；
- `allowed_substitutions`：只允許 `{IDENTITY}`、`{OUTFIT}`、`{PROP}`、`{ACTION_OR_SKILL}` 四類語意變數，並明列實作模板映射（例如 `IDENTITY → {CID}+{NAME}+{APPEAR}`）；其中 `{APPEAR}` 只描述角色固有外觀，不得夾帶風格、比例或生成參數；
- `acceptance_anchors`：原生 1×、nearest-neighbor 放大與引擎實際顯示尺度三種驗收錨圖。

### 複用規則

1. **鎖定配方骨架**：模型、參數、尺寸、參考圖分工、幀序、比例語句、負向限制與後處理不變。
2. **只替換白名單變數**：預設只換 `{IDENTITY}`、`{OUTFIT}`、`{ACTION_OR_SKILL}`、`{PROP}`；若要改骨架，必須另開新 recipe 版本，不能假裝仍是同配方。
3. **先做一個 pilot**：與合格舊素材在原生 1×、nearest-neighbor 放大及引擎實際畫面三處並排；風格、比例、邊緣、色盤、基線、動作可讀性任一不符就停，不 fan-out。
4. **來源不完整才反推**：先明列已知／未知欄位並標記 `lineage_incomplete`；只能用既有成品反推一個 pilot，禁止直接批量。找到新證據後要回填 recipe，不能讓猜測永久冒充原配方。

這個閘門適用於像素角色、戰鬥 sheet、立繪差分、UI 插圖、場景系列與特效素材；重點不是「提示詞寫得像」，而是讓同一系列的**完整生產條件可重現**。

## §1 場景管線決策（最重要的一節）

### 決策樹

| 要產的東西 | 管線 | 理由 |
|---|---|---|
| **場景**（房間、樓層剖面、靜態空間） | **整張全生成 → 摳互動件 → 引擎疊層** | 一張圖內光影、色調、投影天然統一＝「設定集感」 |
| **角色／動態物**（人物、動作幀、會換位置的東西） | **離散 sprite**（獨立生成、去背、正規化） | 要走動、要換姿勢、要跨場景複用 |
| **tile 化重複地形**（俯視 RPG／平台關卡等 tile-based 場景） | **TileMapLayer 工作流（4.3+）** | 重複鋪面用 tile 而非整張生成；作法見 godot-pixel-art.md §4 |

### ❌ 反面教材：逐件生成拼裝（踩過整輪，別再走）

曾把場景也拆成「一件件家具獨立生成→引擎拼裝」——**AI 逐件生成無法統一光影**：每件的光源方向、色溫、明度基準各自為政，拼起來就是**貼紙感**（物件浮在地板上、彼此不像同一個世界）。實戰上整批 26 件側視物件＋離散拼裝的架構最終整批作廢，轉向整張全生成後才解決。**光影統一是「生成時」的性質，不是「拼裝時」能補救的性質。**

### ✅ 正面管線：整張全生成 → 摳互動件 → 引擎疊層

1. **整張全生成**：整層場景一張圖生成（例：public_floor.png 1024×1536 等角剖面）。格局先過 `interior-space-sanity`（產前把約束寫進 prompt、產後跑審圖表）；投影制式（flat 或等角，擇一）寫死在工單。
2. **原位摳互動件**：用 `cut_iso_objects.py` 依多邊形 spec 從底圖**原位**摳出互動件 → `objects_iso/*.png` ＋ `anchors.json`（記錄每件的底圖座標）。互動件＝「疊在原位的複本」——底圖上物件仍在，引擎在 anchor 座標蓋上互動件或其差分即可。摳圖鐵則：多邊形完整包住物件（絕不切進本體）、不含入其他互動件；可含少量貼邊背景像素（原位貼回像素恆等）。
3. **機械自檢 diff=0**：每件按 anchor 貼回底圖，逐像素 diff **必須為 0**（`cut_iso_objects.py check`）。這是整條管線的正確性錨——diff=0 保證「摳出來的就是原圖那塊」，之後任何差分（燈亮/燈暗/使用中）只改物件像素、背景原樣。
4. **引擎疊層**：底圖鋪底 → 互動件按 anchors 疊回 → 角色 sprite 按 y 座標 z-sort（painter's algorithm）插入層間 → 差分/狀態換圖只換互動件那層。
5. **底圖外擴不動本體**：底圖要改尺寸（如滿版外擴）時，原圖最後**整張貼回**新畫布 → 裁回 diff=0 天生保證；記錄 offset（如 x=+115），anchors 全體平移即可沿用（`make_public_floor_wide.py` 範式）。

### 互動房間例外：高接觸生活物件走 object-layer，不用整圖硬補

若目標是生活沙盒房間，且床、工作桌、沙發、陽台椅、浴室、衣櫃等物件需要角色坐、躺、工作、洗澡、換衣或更換服裝，不要把「整張全生成 → 原位摳互動件」當唯一答案。實戰已證明：完整底圖畫滿家具後再硬摳、貼片、修座標，會反覆產生錯位、殘留狀態、背景 patch、人物剪貼感。

此類房間先走 object-layer gate：

1. 生成或繪製乾淨 `base_architecture`，只含牆、地板、門洞、窗洞、濕區殼、陽台平台等建築層。
2. 每個家具/設備都是 `object_node`，含 idle sprite、hitbox、blocked area、nav point、act anchor、baseline_y、z band。
3. 每個高接觸物件必有 front mask、active/state sprite、outfit-specific actor pose、interaction timeline、cleanup/reset。
4. 互動素材不要連整房背景一起做；只做該物件、必要前景遮擋、角色姿勢與狀態層。
5. 靜態 montage 只當 smoke test；完成驗收要有 walkthrough 或 phase trace，逐步檢查 approach → align → mount/sit/lie/use → acting → exit cleanup。

高接觸物件的最低證據：idle 對位、active 對位、角色姿勢對位、前景遮擋合理、離開後狀態恢復或有設計理由持續、服裝/立繪/台詞同步。若結果看起來像半透明示意、人物剪貼或站在旁邊，就 Fail。

### 留白設計（產底圖時就要想）

底圖生成時**刻意留空位**——桌面留空、牆面留白、角落留地——給日後「動態個性小物」當疊加層（角色私人物品、事件道具、季節裝飾）。底圖畫太滿＝疊加層無處落、個性化只能重生成整張。

### 「AI 畫不穩 × 要互動」的元素 → 底圖只畫開口、離散件疊層（門策略，可推廣）

門片 AI 一直畫錯（懸空、截短，重生成也壓不住）→ 不再硬拼 prompt，換維度：**底圖只畫乾淨門洞／凹龕，門片自製離散件疊上**——AI 只畫它畫得穩的（開口），畫不穩又要互動的元素改自製疊層，順便**免費拿到開關互動**（換圖即開關）。凡「AI 畫不穩 × 遊戲要互動」的元素皆適用此策略。

互動門定案（可直接沿用）：
- **旋開門＝「開貼牆」兩態**、**淋浴間衣櫃＝推拉兩態**；**不做旋轉弧動畫**——等角投影下門片旋轉的透視變形成本太高，兩態切換已足夠。
- **門洞加 waypoint**：角色動線「站門前 → 暫停 → 開門 → 通過 → 關門」，門成為活的場景節拍而非裝飾。

## §2 驗收基準＝與範例圖並排比對（不是規格表打勾）

**血淚**：曾發生規格逐條全過（尺寸✓投影✓色數✓元素齊✓）但成品与風格範例並排一看**就是不像**——白做。規格表驗的是「合法」，並排比對驗的是「像不像這個遊戲的圖」。

**執行法**：
- 每張美術工單**必附風格錨圖**（範例圖／已定稿場景／atmosphere refs），驗收時把成品與錨圖**並排開在同一畫面**比對：色調、明度分佈、投影、線條質感、密度。
- 「與範例並排比對通過」是驗收的**最後一關且一票否決**；規格表只是前置過濾。
- 引擎內驗收同理：截圖與定稿場景並排，看新舊元素是否同一世界（例：程序化城市剪影第一版窗燈懸浮＝「彩點雨」，並排立刻看出；改為「比夜空亮的中灰藍建物形體＋整層點燈簇狀」才成立）。

## §3 鐵則集（每條都踩過才寫進來）

1. **Pilot 先行**：批量生成前先產 1 件給使用者／審圖 agent 過目，硬傷關掉才 fan-out。pilot 沒過就 fan-out＝整批重產。
2. **投影全場一致**：flat（平面側視）或等角（isometric），全場**擇一**；每張美術工單**寫死投影宣告＋附場景錨圖**。曾發生物件 3/4 斜視（露頂面）疊在平面 2D 場景上，突兀到整批重產。pilot 首驗第一項就是投影一致。
3. **空間合理性外包給 `interior-space-sanity`**：室內格局的動線／連通／樓梯／乾濕分區／AI 空間幻覺，產前產後照該 Skill 的原則庫與檢查表走，本 Skill 不重複維護。
4. **特殊尺寸幀的比例鐵則**：舉手／伸展等「超出標準身高」的動作幀，畫布加高（如 480 vs 標準 300）、身體仍畫在標準高度、多出部分向上延伸；引擎端偵測「畫布高≥閾值 → 畫成 target_h×1.6、**腳線對齊**」——人不會因舉手變高，頭腳比例與正常幀一致。
5. **產圖自評不可信，用量化驗證**：產圖 agent 自稱「真像素」實為 17–20 萬色 faux-pixel。驗收用可量化手段取代目視自述：**色數統計**（真像素≤數百色）、**貼回 diff**（=0 才過）、**放大 grid 檢查**（像素格是否對齊）。量化驗收的完整機械前哨（色盤白名單／alpha 二值／mixels 往返測試）見 `References/pixel-art-fundamentals.md` §6。
6. **Async agent 結果必驗「非空＋切題」**：背景 agent 可能回傳無關內容或空結果（tool_uses=0）；收割時先驗非空且切題，失敗即重派，**別當成功往下走**。
7. **等角三假影必查**：懸空門／截短門／幻影光斑——判別與修正措辭詳見 `interior-space-sanity` SKILL §4「等角剖面特有結構假影」（引用即可，本 Skill 不重複維護）；**設計期**就避免把窗畫在會被剖除的近側牆，別等產後才修。
8. **已驗收構圖做單點修正 → 必附上一版成品圖當「構圖鎖」**：純文字模板（即使含完整格局規格）鎖不住生成模型的構圖重擲——曾只加一條光斑修正文字，整層格局被重擲（七門洞座標只中 2/7、陽台縮水）；改為**附已驗收成品圖當構圖鎖附圖＋模板明寫「唯一允許差異＝X」**後，門洞命中 7/7 且產速更快（271s vs 624s）。通則：**單點迭代＝成品錨＋白名單差異**；等同像素動作批「附 idle 鎖外觀、只借姿勢」recipe 的構圖版。
9. **既有系列先追生成譜系，不從成品目測重造**：只要原 sheet、prompt、模型參數、尺寸、參考圖分工或後處理紀錄仍可取得，就先完成 §0.5 provenance preflight，複用已驗收 recipe 並只替換白名單變數。來源缺失時才可標記 `lineage_incomplete` 反推，且仍須 pilot 通過才能擴產。
10. **新寫 prompt 套三句式（敘事方言模型）**：①變與不變分開講（「最大程度保留⋯（條列）」＋「重新設計⋯但保留（條列）」——鐵則 8 的構圖鎖即其附圖版）②負約束配替代（「沒有⋯只有⋯」，不留真空）③行為/材質代抽象詞（不寫「有氛圍」，寫材質與光線）。三句式經換裝差分 A/B 實測：無此結構時，同一角色的差分會明顯漂移到近乎換人。
11. **多幀動作 sheet 走「尺度三層防線」（sprite-forge 吸收，2026-08）**：①生成端——已驗收 master frame 鋪滿格子當**錨定模板**連同原圖餵產圖，「只改姿勢，禁止 zoom」（＝鐵則 8 構圖鎖的動作幀版）②處理端——從驗收幀建 **scale profile**（鎖 cell/縮放/anchor/trim），整個動作包共用，禁逐動作重算③驗收端——**數值 QC gate**：身體尺度變異 `body_scale_cv≤0.08`、腳線漂移 `anchor_y_std≤0.05`、`edge_touch=0`、跨動作 drift≤0.08，身高差 >10-15% 退件；**QC 失敗＝重新生成訊號，禁止用逐幀縮放把漂移藏起來**。配套格律：動畫本體禁 raw 單列（4 幀→2x2、9→3x3）；混動作 atlas 禁一次生成（逐動作產＋QC 後才組裝）；**主體與寬 FX 必分 sheet**（刀光/彈道另開，否則 FX bbox 把身體壓小）。原文全文：`References/vendor-sprite-forge/generate2dsprite/`（含特殊形體契約：長形生物鎖剪影包絡／Boss 鎖腳／地面火焰鎖起火線）。
12. **可玩地圖走分層契約，不交付烘死大圖（sprite-forge 吸收）**：base 只畫地面——一切 runtime 物件（樹/門/箱/NPC）不得烘進 base，烘進去就重生；流程 base→in-world reference（≤9 候選物、禁畫箭頭標註）→逐物分類（compact/wide/tall/collision-bearing/strip 決定產圖策略）→產素材→**擺放/碰撞 JSON**（sortY／occlusionClass／actorSafeArea／occupantPolicy）→合成 QA 預覽。「一張大圖＋hitbox＝有碰撞的背景，不是關卡」。schema 與模板：`References/vendor-sprite-forge/generate2dmap/references/layered-map-contract.md`。

## §4 工具鏈（管線需要的六支腳本，規格如下）

> 以下是本管線實際跑起來所需的腳本規格。專案內自行實作即可——**重點是每支腳本的「要點」欄，那是踩過坑後才定下來的行為契約**。

| 腳本 | 用途 | 要點 |
|---|---|---|
| `cut_iso_objects.py` | 從整層底圖**原位摳互動件**，三模式：`cut`（依 polygon spec 摳圖→PNG＋anchors.json）／`verify`（產描邊疊圖＋棋盤格驗證圖）／`check`（每件貼回底圖 diff 必須=0 的機械自檢） | 本管線核心；spec 為 `cut_spec.json`（source＋每件 polygon），座標一律底圖原座標系 |
| `make_public_floor_wide.py` | 底圖滿版**外擴**範式：左右各延伸屋外環境（漸層＋星點＋程序化剪影，調色盤實測自原圖）＋24px 接縫羽化；**原圖最後整張貼回→裁回 diff=0 腳本內 assert** | 改尺寸不動本體的範本；輸出附 offset 供 anchors 平移 |
| `key_object.py` | **單色 key 底（如 #FF00FF／#00FF00）單物件去背**成透明 PNG：de-blend＋despill→去雜點（保留多連通域，支援多件式物件）→貼齊內容邊界裁切（底列=接地線），輸出原生比例 RGBA | 給離散物件路線用；不套人物固定畫布、不做高度正規化 |
| `art_dispatcher.py` | 產圖批次調度器：本進程親自 spawn 子進程（exit code＝死活，不用猜）＋台帳單一寫者防重複發包＋額度上限**熔斷**停發、留 resume 點重跑即續 | 根治「背景任務死活不明→誤判重發→雙倍燒額度」；批量產圖一律經此，不手發 |
| `make_tile.py` | 滿版材質→**無縫平鋪 tile**：梯度修正法（邊差沿全幅線性攤平，只加低頻修正、保留原始紋理，無鬼影/無對角干涉）＋`--test` 出 NxN 平鋪圖目視驗縫 | 地板/牆面鋪面用；不去背不裁切 |
| `References/vendor-sprite-forge/generate2dsprite/scripts/generate2dsprite.py` | 多幀 sheet **確定性處理器**（MIT vendor）：去背→固定格切→feet-anchor 對齊（98 百分位腳線）→`fit`/`preserve` 縮放→QC 統計→Godot sprite3d/bundle JSON 合約 | ⚠ key 色寫死洋紅 #FF00FF——若你的產線用別的 key 色（如綠幕 #00FF00）需改參數或改用自家 `key_object.py`；同目錄 `make_anchor_layout.py`（錨定模板產生器）、`../generate2dmap/scripts/`（prop pack 抽取／terrain 切片） |

## §5 引擎模式（Godot 4，經 C0–C2 實戰）

> 本節為**自繪 `_draw()` immediate-mode 架構**的實戰特化；標準 node-based 專案的對應做法（TileMapLayer、`y_sort_enabled` 天然 z-sort、Camera2D 像素設定、Parallax2D）見 `godot-game-dev` Skill 的 `References/godot-pixel-art.md`——兩套並存，按專案架構選用。

- **底圖 fit＋anchors offset 疊層**：底圖等比 fit 進視窗，互動件用 anchors.json 座標（乘同一縮放、加同一 offset）疊回；底圖外擴後全體 anchors 加 offset 即沿用。
- **z-sort（painter's algorithm）**：角色與互動件按接地 y 座標排序後由後往前畫，角色自然走進物件前後。
- **zone 互動狀態機**：`home → toZone →（waypoint 走動）→ acting（播該物件互動動畫）→ home`——場景是「角色走到物件旁做事」，不是站樁換背景。
- **Diegetic UI**：數值顯示貼在**場景內物件表面**（電視螢幕內容、金屬牆面標示牌，自發光＋內嵌值條＋狀態詞），不做懸浮玻璃 HUD；UI 標題與場景內指標牌用 scrim 分開視覺層級。
- **GDScript 兩道機械防線**：①Variant 必標型——`var x := dict.get(k)` 會 `Cannot infer type`，凡右側是 `Dictionary.get`/JSON 值一律 `var x: float = ...`（踩 2 次）；②收工必跑 `Godot --path app --headless --quit-after N`，無 `SCRIPT ERROR` 才算過（= GDScript 的 py_compile／lint 前哨）。貼圖載入失敗必 fallback 色塊，不讓 `_draw` 崩畫面。
- **測試 affordance 內建**：留環境變數覆寫時鐘（如 `GAME_HOUR=22`）、強制全員在場模式、`-- screenshot` 截圖模式——作息／時段驅動的場景不留這些，驗收只能空等真實時間到。
- **shader 光影分工**（§1「光影統一是生成時性質」不變，這是它的引擎端補集）：底圖走整張全生成保完美統一；**動態件／未烤進底圖的疊件走 relight shader**——`SCREEN_UV`＋全域光參數（時段色溫等），**一個共用材質點亮整層疊件**，融入度可救回七八成；**負載發光 glow**（additive，load 值走 `modulate.a` 逐件帶入）＝把監控數值 diegetic 化為物件自體發光。分工原則：美術手工做不到的**執行期動態**才交給 shader，做得到的留在生成期。
- **immediate-mode `_draw()` 的 shader 限制**：`_draw()` 無 per-draw material——預設走**路徑 A**「層拆分＋共用材質＋`modulate` 帶純量」（一層一個 CanvasItem 掛共用 ShaderMaterial，per-件參數塞 modulate 通道）；只有需要 shader 件與一般件**精準 z 交錯**時才升級**路徑 B**（RenderingServer 手排 canvas item）。
- **一鍵驗收＋回歸地板：開專案就建，不等出事**——驗收腳本的範式：參數化（模式／時段可指定）、headless parse 前哨、`try/finally` 還原測試前狀態、`subprocess` 明定 `encoding='utf-8'`（Windows cp950 防線）；搭一份 `REGRESSION_CHECKLIST.md` 分**自動層＋目視層**，**每個踩過的坑落成一條檢查項**。headless 鐵則：`--headless --quit-after N` 兩者齊給，否則殭屍進程堆積。

## §6 協作分工（設計 agent × 執行 agent × 終審）

| 角色 | 職責 | 鐵則 |
|---|---|---|
| **設計 agent**（game-visual-storyteller 等） | 出**座標級**空間/版面規格（哪面牆、幾 px、什麼關係） | 工程師不自切格局（自切 2×2 均分被打回）；給設計 agent 痛點＋約束＋尺寸 |
| **執行 agent 工單** | 照規格執行（程式／產圖） | 六元素合約（目標／範疇／輸入／輸出／驗收／邊界）；**邊界節明列「不可改的既有常數／命名」**（曾被悄改角色名） |
| **終審** | **親跑**驗收指令（headless parse、diff 自檢、截圖並排比對），不信 agent 自述 | 審核層永不外包 |
| **critic 定期掃** | 連續多輪工單後掃**迭代殘留**：死碼堆積（曾清 17 函式 239 行）、被悄改的既有值、`_legacy` 垃圾 | 多輪迭代必排，不等出事 |

另：實作前**重讀自己的規格**、每輪完成對照 spec 問「照構想延伸了嗎」——**規格寫了卻零碎實作**是這條管線最貴的流程教訓；專案開工即建 WORKLOG（一次工作一則）。

### 專職 agent 路由（每類問題有專職，不用通用執行層打天下）

| 問題類型 | 專職 agent |
|---|---|
| 引擎邏輯／FSM／互動狀態機 | `godot-gameplay-scripter` |
| shader／光影特效 | `godot-shader-developer` |
| 資產進引擎（匯入／打包／動畫設定） | `game-technical-artist` |
| 空間鄰接／動線設計 | `level-designer` |
| 風格／氛圍／視覺敘事 | `game-visual-storyteller` |
| 批量產圖調度 | 產圖調度 agent（走 §4 `art_dispatcher.py`，不手發） |
| 驗收自動化（一鍵驗收腳本／回歸） | `e2e-testing-engineer` |
| 觸控／UI 稽核 | `ui-ux-reviewer`（校準法見 §7） |
| 程式審查 | `critic` |

### 多 agent 並行的檔案鎖紀律

- **動同一檔的工單排隊，不並行**：例——門系統正在改主場景腳本時，同樣要動它的 UI 修正／glow 整合**排隊打包**成下一輪；不同檔才並行。
- **雙 dispatcher 會互踩台帳**：兩個調度器寫同一份台帳＝競爭寫壞，**per-queue 台帳**（一佇列一份）根治。
- **跨 session 的 agent 會被清**：背景 agent 的工作狀態不可依賴——重要素材／報告**全落磁碟**（含中間產物與結論），新 agent 憑磁碟檔案即可無縫接手。

## §7 UX 稽核按情境校準（ambient 桌寵／kiosk 類）

UI 驗收不套通用 checklist 打勾——ambient 桌寵／kiosk 類（遠距離看、觸控為主、常駐桌面）按情境校準稽核尺：

- **觸控目標從程式碼常數量「真實 mm」**：例：44pt 在 10 吋螢幕 ≈6.9mm——pt/px 達標不等於指頭按得到，換算成實體尺寸才算數。
- **CJK 字級按觀看距離驗**：桌距可讀性——狀態詞 **≥14px** 為底線。
- **文字疊圖必加 scrim**：≥0.6 不透明度墊層，否則底圖一換文字就淹沒。
- **命中框可大於視覺框**：小圖示保持視覺精緻，touch target 另開更大命中框。
- **手勢語言全域一致**：同一手勢全 app 同義——「點角色＝聚焦」就不能在某處變成「點角色＝退出」。
